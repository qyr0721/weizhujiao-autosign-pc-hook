## 1. 抓到的四个真 bug

### Bug 1（致命）：域名正则匹配不上真实 API 域名

```js
var SIGN_RE = /teachermate\.cn/i;   // 错
```

API 在 `www.teachermate.com.cn`，页面在 `v18.teachermate.cn`。`teachermate\.cn` 要求 `teachermate` 后紧跟 `.cn`，而真实域名是 `teachermate` + `.com` + `.cn`，**中间多了 `.com`**。

追踪证据（在 `capture()` 入口打的临时日志）：

```
TRACE abs= "https://www.teachermate.com.cn/wechat-api/v1/class-attendance/student/active_signs"
      re= /teachermate\.cn/i
      test= false        <-- 明明字符串里就有 teachermate
```

后果：钩子对**所有真实 API 请求**都不生效 → `openId` 永远学不到、`apiBase` 永远是默认值、`lastReq` 永远是 null。而且是**静默失败**：不报错、日志只有 installed/started，看起来一切正常。

修复：`/teachermate\.(?:com\.)?cn/i`。测试锁死（"fetch 钩子捕获到 teachermate.com.cn 的请求"）。

> 这个 bug 说明一件事：**"看起来跑通了"和"真的跑通了"之间只差一次带真实域名的断言。**

### Bug 2（致命）：`apiBase` 只能靠"已发生的请求"反推

原逻辑：`state.apiBase` 初始为空，只有捕获到请求才 `adoptApiBase()`；而 `req()` 在 `apiBase` 为空时直接 `Promise.reject("apiBase-unknown")`。

后果：如果页面在我注入**之前**就加载完（正常情况都是这样），注入后没有任何新请求 → agent 永远学不到基址 → 每次 `signNow()` 都立刻空转失败。

修复：内置默认基址 `https://www.teachermate.com.cn/wechat-api/v1/class-attendance`（与 `signer.py` 同一份契约），捕获到真实请求时再修正。

### Bug 3：`status()` 经日志泄漏带 openid 的完整 URL

`status()` 是**设计给主机侧轮询并落盘**的接口，里面包含 `log` 数组。而安装日志记录的是：

```js
log("installed", { href: location.href.slice(0, 120) });   // 带 ?openid=xxxx
```

结果 `JSON.stringify(status())` 里含 32 位 hex 凭证。这与"凭证不出页面"的设计原则直接冲突，而且会被写进 `state.json` / 日志文件。

修复：`safeHref()` 只取 `origin + pathname`，日志中不再出现 query。测试锁死（"status() 不外泄凭证本体"）。

### Bug 4：`installXhrHook` 缺能力校验，会拖垮整个 agent

```js
var P = window.XMLHttpRequest && window.XMLHttpRequest.prototype;
if (!P || P.open.__wz) return;      // P.open 为 undefined 时直接抛 TypeError
```

真页面上 XHR 可能被延迟定义、被代理改写、或只在特定页面存在。一旦 `P.open` 不存在，异常发生在**装配阶段**，导致整个 agent（包括已经装好的 fetch 钩子）全部失败。

实测栈：

```
TypeError: Cannot read properties of undefined (reading '__wz')
    at installXhrHook (page_agent.js:159:26)
    at page_agent.js:305:5
```

修复：加 `typeof P.open !== "function" || typeof P.send !== "function"` 守卫。

## 2. 一次"假警报"（值得记下来）

首轮测试有 3 条失败，排查后是**测试环境问题，agent 行为正确**：

```
FAIL  signNow 发出 1 次 active_signs
```

原因是测试在**凌晨 00:0x** 跑，而 `classHours` 默认 `[7,23)`，`inClassHours()` 正确地拒绝轮询。修的是测试（显式 `onlyClassHours:false`），不是产品代码。

> 但它反过来验证了一件重要的事：**时段闸门确实生效**，不会在半夜乱发请求。

## 3. 覆盖了哪些行为契约（agent 21 条）

| 类别 | 断言 |
|---|---|
| 注入 | 返回 `installed`；挂上 `__wzSignAgent` 且版本正确 |
| 凭证 | 从 URL query 自举；`status()` 不外泄凭证本体 |
| 轮询 | 恰好 1 次 `active_signs`；路径正确；`credentials:include`；带 `openId` 头 |
| 提交 | 命中后 1 次 `student-sign-in`；body 含 `signId/courseId`；POST；`Content-Type` |
| 幂等 | 同一 `signId` 不重复提交；`errorCode 305`/`repeat sign in` 视为已签到 |
| 失败 | 401 → `auth=expired`；**且绝不自行导航**（保住可用页面） |
| 定位 | `isGPS` 且有 `pos` 时带坐标 |
| 钩子 | fetch 钩子捕获 `.com.cn` 请求；新 `openId` 被采纳并被后续请求沿用；XHR 同上 |

## 4. 覆盖了哪些判定（classify 12 条）

- 新 target 优先 → `NATIVE_WINDOW`
- `waerrpage`/`jump2h5err` → `BLOCKED`
- 极小 body + `micromessenger` → `STUB`
- 大 body + 授权文案 → `INTERCEPTED`
- 大 body 但无授权特征 → `UNKNOWN`（**不谎报成功**）
- redirect_uri 编码、内部无裸 `&`、`#wechat_redirect` 结尾、`--authorize-url` 覆盖
