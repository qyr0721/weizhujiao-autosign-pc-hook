# 三条限制的解除路径 —— 工程方案与实测记录

> 针对上一版方案 §5.1 / §5.2 提出的三条限制：
> ① 不能触发授权 ② 必须先开小程序且全程不能关 ③ 同一时刻只能一个 CDP 客户端
>
> **这三条性质完全不同**：③ 是我们自己的代码缺陷（可直接修）；② 是结构性依赖（可自动化，无法凭空创造）；① 是**我上一轮测量错了对象**得出的过强结论（需重测）。
> 本文所有"C 已实现"项都附了实际运行输出；"待跑"项给了可判定的实验，不假装已完成。

## 0. 结论表

| # | 限制 | 性质 | 处置 | 状态 |
|---|---|---|---|---|
| ③ | 只能一个 CDP 客户端 | **代码缺陷**：proxy 透传 id + 上行广播 | id 重写复用代理（`src/proxy-mux.ts`） | ✅ 已实现并通过离线测试 |
| ② | 必须先开小程序点火、且不能关 | **结构性**：调试客户端只在 `OnLoadStart` 创建 | 三层：自愈 → 自动点火 → 结构消除探针 | ⚠️ 自愈/自动点火已实现并实测；结构消除待跑探针 |
| ① | 不能触发授权 | **测量偏差**：在 liteapp 容器页上测的，不是服务号 H5 | 用 per-tab 附着在正确上下文重测（三种变体） | ⚠️ 工具已就绪，需在有 H5 标签时跑一次 |

## 1. 限制 ③：多 CDP 客户端 —— 已修

### 1.1 根因（在 `src/index.ts` 里）

```ts
// 下行：客户端消息原样塞进 payload，id 不做任何变换
debugMessageEmitter.on("proxymessage", ...)   // 广播给所有小程序 WS

// 上行：把结果广播给所有 CDP 客户端
onMessage = (message) => { if (category === "chromeDevtoolsResult")
                             debugMessageEmitter.emit("cdpmessage", payload); }
```

两个客户端各自从 `id=1` 开始计数，同一条上游连接上就出现重复 id；回复又被**广播**，于是 A 收到 B 的结果、B 收到 A 的。上一轮"两个脚本一起跑监听进程崩溃"就是这个。

### 1.2 修法：标准 CDP 多路复用（id 重写）

`src/proxy-mux.ts`：

```
客户端 -> 上游：分配全局唯一 gid，登记 gid -> (客户端, 本地 id)，改 id 后下发
上游 -> 客户端：有 id 的是应答，查表还原本地 id，只发给发起者
                无 id 的是事件（frameNavigated / consoleAPICalled），广播
```

关键取舍：**应答单播、事件广播**。事件广播是必要的——DevTools 的 Network/Console 面板和我们的脚本都要看事件；而应答必须单播，否则 id 语义就崩了。

### 1.3 实测结果

离线测试（不需要微信）：`node node_modules/tsx/dist/cli.mjs test/mux_test.ts`

```

  PASS  上游收到 2 条命令

  PASS  命令内容未被破坏

  PASS  B 未收到 A 的回复

  PASS  事件广播到两个客户端
```

真实启动（frida 注入 + mux 代理）：

### 1.4 用法与残余

- 默认启用；要回到原行为加 `--legacy-proxy`。
- 现在可以：**DevTools（`devtools://...?ws=127.0.0.1:62000`）与 `cdp_sign_agent.py` 同时在线**，也可以同时跑 `trigger_oauth.py`。
- 残余：多客户端各自 `Target.attachToTarget` 同一标签页会拿到**不同 sessionId**（这是对的，互不干扰）；但 DevTools 的 Element 面板本来就不实时，多客户端不会改善它。
- 注意：`channel_keeper.py` 的健康探测每 5s 连一次 62000，**依赖 mux 才安全**（`--legacy-proxy` 下请把 `--interval` 调大或改用 `--check-only`）。

## 2. 限制 ②：点火与常驻 —— 采用「常驻」而不是「自动点火」

> **2026-10-25 决策更新**：用户明确选择「**保留一个小程序在后台常驻**，不必每次都打开」。
> 因此本节的下文（自动点火）降级为**可选**，`channel_keeper.py` 已改为**默认不点火**：
> 断连只提示一次（"切前台再切回 / 重开"），绝不操作界面；要自动点火必须显式加
> `--ignite-cmd` / `--ignite-deeplink` / `--ignite-uia`。
> 代理也改成"死了才拉、最多 3 次"——因为**代理重启会切断 9421 的旧连接**，重启后必须重新触发一次小程序。

### 2.1 为什么它是结构性的

看 hook 的位置就知道：`OnLoadStart` 是**小程序启动**的回调。`remoteDebugMode=1` 与 `ws://localhost:9421` 都写在**那一次启动的 config 结构体**里，随后由小程序运行时的远程调试客户端去拨号。也就是说：

> 调试传输层的**生命周期 = 某次小程序启动的生命周期**。

不开小程序 → 没有客户端 → 9421 上没有下游 → 一切 CDP 请求都无响应。关掉小程序 → 客户端销毁 → 通道断。这不是配置问题，是设计如此。

所以只能从两头下手：**让"开小程序"这件事不需要人**，或者**证明拨号点可以被我们直接调用**。

### 2.2 L1｜自愈：`channel_keeper.py`（已实现并实测）

三态探测（只看 62000 就能判，不依赖代理的 stdout）：

| 状态 | 判据 | 动作 |
|---|---|---|
| `PROXY_DOWN` | 62000 端口不通 | 拉起代理（含 frida 注入），等端口就绪 |
| `CHANNEL_DOWN` | 端口在，但 `Target.getTargets` 无应答 | 过了 grace 就点火，指数退避（25s → 封顶 150s） |
| `CHANNEL_UP` | 有应答 | 若 target 列表里出现签到页，托管 `cdp_sign_agent.py` |

实测（`--grace 3 --interval 3 --run-for 40`）：

```
[23:50:51] [+] 代理已就绪
[23:50:57] [=] CHANNEL_DOWN (no-reply)
[23:51:06] [!] 通道断了，但没有配置任何点火手段。请在微信里打开任意小程序。
[23:51:36] [*] 达到 --run-for，正常退出
=== 端口残留: （无）
```

过程中修掉了一个自造缺陷：最初 `probe_channel` 把**任何** WS 异常都判成 `PROXY_DOWN`，会触发重复拉起（重复 frida attach + 端口二次绑定）。现在只有**端口确实关闭**才算代理死亡，WS 层异常一律降级为 `CHANNEL_DOWN`。修复后 40s 内无重复拉起、退出无残留端口。

**效果**：代理重启后必须"再开一次小程序"这个隐藏步骤消失了；小程序被关掉后，守护会在 grace + 一次点火内把通道拉回来，agent 自动重新附着。

### 2.3 L2｜自动点火：三种手段，按可靠性排序

```bash
python channel_keeper.py --ignite-cmd  "<你的 UI 自动化命令>"     # 最稳：复用已有能力
python channel_keeper.py --ignite-deeplink "weixin://dl/business/?t=<ticket>"
python channel_keeper.py --ignite-uia  "<模板名>"                 # 复用 auth_refresher 的 locate_click
```

- **`--ignite-cmd` 优先**：`weizhujiao-autosign-pc/auth_refresher.py` 里已经有 `find_wechat / force_foreground / grab / locate / locate_click`，是现成的模板点击链路。点火就是"点开一个常驻小程序"，比点微助教菜单简单得多，你现有的模板匹配能力足够。
- **`--ignite-deeplink`**：`weixin://` 协议已注册，`os.startfile` 即可；但 `dl/business/?t=` 需要有效 ticket（会过期），适合把某个长期有效的入口链接写进配置。
- **`--ignite-uia`**：直接 import `auth_refresher`，用模板名点击。需要你在 `templates/` 里补一张"小程序入口"的模板。
- 三者都没配 → 打印明确指引，**不空转**（避免无限重试把微信点乱）。

### 2.4 L3｜结构消除：`probe_dialer.py`（工具就绪，实验待跑）

思路：既然拨号发生在浏览器进程里，就 hook 网络层，直接看**是谁在拨 9421**。

```bash
python probe_dialer.py --seconds 120
# 另开一个窗口，在微信里打开任意小程序，观察输出
```

输出形如（示意）：

```
[+] ready: pid=51240 flue=0x7ffd57f40000 modules=119 port=9421
[DIALER] via connect
   #0  ws2_32.dll!connect+0x...
   #1  flue.dll!<符号>+0x2d5a2xx        <- 拨号点
   #2  flue.dll!<符号>+0x...
```

已实测：hook 能干净挂载（`connect` / `WSAConnect` 都找到，`flue.dll` 基址可读），未开小程序时 0 命中 —— 符合预期。

拿到调用栈后有三种结局，对应三种做法：

| 拨号点特征 | 含义 | 做法 |
|---|---|---|
| 通用「远程调试客户端构造/启动」函数 | 可能可以直接调用 | 在代理启动后由 frida 主动调一次 → **点火彻底消失** |
| 只在小程序 AppIndex 上下文里可达 | 结构性绑定 | 接受 L1+L2；或在 `WebViewController` 侧找等价入口 |
| H5 标签页也走同一函数 | 说明 H5 本可自己建调试客户端 | 改 hook 点，让 H5 也建立会话 → **连小程序都不需要** |

> 第三种若成立，本方案的最大前置条件就消失了。这也是为什么这个探针值得先跑——成本 2 分钟，收益是整条前置链路。
> 若 `ws2_32.connect` 无命中（比如走 WinHTTP 的 WebSocket），脚本已在末尾提示改 hook `winhttp.dll!WinHttpWebSocketCompleteUpgrade`。

### 2.5 残余（诚实清单）

- 不能**保证**免点火：L3 未验证前，点火仍是必需动作，只是**不再需要人**。
- 小程序被关 = 通道断 = 断连窗口内可能漏掉签到。keeper 把窗口压到 grace(15s)+点火时间，仍非零。
- 点火动作本身会抢焦点/移动鼠标（UIA 方案），在你看屏幕时会很烦；建议用 `--ignite-cmd` 走后台方案，或固定用一个不占前台的入口。

## 3. 限制 ①：不能触发授权 —— 上一轮的结论需要修正

### 3.1 测量偏差在哪

上一轮"路径 B"的记录是「从**普通 page target** 导航到授权链接」，实际落在 `liteapp.weixin.qq.com` 或 applet 容器页上。而：

- `liteapp.weixin.qq.com` 是 **AppIndex 的宿主页**（小程序容器），导航策略、域名白名单、原生拦截闸门都属于小程序域；
- 真正的服务号 H5 是 `v18.teachermate.cn/...student/sign` 这类普通 `page` target。

两者共用**同一个调试通道**，但不共用**导航策略**。用前者的失败推出"PC 微信不会在 webview 里处理 OAuth"，样本选错了。

更关键的是：当时没有 `Target.attachToTarget` 的 per-tab 会话，只能用 `pick_page()` 抓"第一个 http target"，恰好抓到容器页。现在 EXTENSION.md 给了按 `targetId` 精确附着的办法，这个实验可以重做。

### 3.2 三种发起方式，机理不同

| 变体 | 机制 | 为什么值得单独测 |
|---|---|---|
| `href` | 页面内 `location.href = authorize` | **渲染器发起**，走正常导航管线，最接近用户真实点击 H5 链接 |
| `open` | 页面内 `window.open(authorize)` | 可能被原生层接管成**新窗口**（PC 微信弹窗授权就是这条路） |
| `nav` | CDP `Page.navigate` | 浏览器侧发起，上一轮用的就是这个，在容器页上失败 |

### 3.3 重测工具：`trigger_oauth.py`

```bash
python trigger_oauth.py --list                 # 看有哪些标签页
python trigger_oauth.py --test-h5 --variant href
python trigger_oauth.py --test-h5 --variant open
python trigger_oauth.py --test-h5 --variant nav
```

安全设计：
- `--test-h5` **只挑普通 H5 标签**，排除 `liteapp` / `servicewechat` / `wxa.wxs.qq.com` / `waerrpage` / 签到页；
- 命中签到页时**拒绝执行**，除非显式 `--allow-sign-page`（导航会毁掉当前授权）；
- 判定表：

| 判定 | 依据 | 后续动作 |
|---|---|---|
| `NATIVE_WINDOW` | 出现新 target | 最好：监听 `Target.targetCreated` 抓新窗口再附着 |
| `INTERCEPTED` | 停在 `open.weixin.qq.com` 且非空壳 | 可把续期写进 agent（仍建议先观察） |
| `STUB` | ~1KB UA 分流空壳 | 这条变体没被接管，换下一个变体 |
| `BLOCKED` | 落 `waerrpage`/`jump2h5err` | 该标签有白名单限制，换普通 H5 标签重测 |

判据说明：`STUB` 的特征是 **body 极小且含 `micromessenger` 字样**（就是那个"是微信就什么都不做"的分流页）；`INTERCEPTED` 则会有真实授权 DOM 或 `微信`/`授权` 文案。两者不会混淆。

### 3.4 如果三种变体全部失败（兜底链）

1. **JSSDK login 兜底**：页内 `WeixinJSBridge.invoke('login', {}, cb)` 可拿 `code`（免 `wx.config` 的旧通道），若微助教存在 `code → session` 的兑换端点，就能**完全绕开 OAuth** 续期。验证办法：看页面 401 后自身的网络请求里有没有带 `code` 的调用。
2. **原生层 replay**：菜单点击最终走 `Weixin.exe` → `WeChatAppEx.exe` 的 mmmojo IPC。用 frida 在主进程按"候选 URL 打开 API + 调用栈"录制一次真实点击，再按栈指纹复现。这是唯一能彻底免人工的方向，但属逆向工作量级（上一轮 `trace_openurl.py` / `ipc_probe.py` 只到侦察）。
3. **接受一次人工**：每月/每天点一次菜单的成本，远低于前两条的工程成本。**这条永远是可接受的终局**。

### 3.5 残余

- 本节的结论**尚未实测**，只有推理与工具。在跑出 `INTERCEPTED` / `NATIVE_WINDOW` 之前，请继续按"授权需人工一次"来设计。
- 即使 `INTERCEPTED` 成立，`snsapi_userinfo` 可能弹授权确认页 —— 那仍需一次点击，只是从"找菜单"变成"点确认"。

## 4. 组合运行（一条命令的全链路）

```bash
# 终端 A：守护（自动拉起代理 + 自动点火 + 自动托管 agent）
python channel_keeper.py --ignite-cmd "<你的点火命令>" --grace 15

# 需要调试时（mux 允许并存）：
#   浏览器打开 devtools://devtools/bundled/inspector.html?ws=127.0.0.1:62000

# 手动介入：
python channel_keeper.py --check-only        # 0=UP 2=CHANNEL_DOWN 3=PROXY_DOWN
python cdp_sign_agent.py --once --observe-only
python trigger_oauth.py --list
```

返回码约定（三个工具一致）：`0` 成功 / `2` 通道通但目标不存在 / `3` 连不上代理 / `4` 通道未建立 / `5` 注入失败。
