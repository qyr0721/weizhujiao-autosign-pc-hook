# 技术复盘：从"必须进微信"到全自动

记录这个项目里踩过的坑和最后的解法，方便后续维护者少走弯路。

---

## 1. 起点：为什么不能"刷网页"

微助教的签到页是 `https://v18.teachermate.cn/wechat-pro-ssr/student/sign?openid=xxx`。

直觉做法是"定时刷新这个页面，看有没有签到"。但实测：

- `openid` **每次进页面都会变**，约 **15 分钟**失效
- 失效后接口一律返回 `401 {"message":"登录信息失效"}`

所以"抓一条链接永久轮询"从一开始就不成立。真正的问题是：**如何低成本地、周期性地重新拿到一个有效 openid**。

---

## 2. 第一次尝试：Xposed 里 hook 微信（失败）

思路很自然：既然要"进微信点菜单"，那就在微信进程里 hook `WebViewUI`，把加载的 URL 抄下来。

用 QuickJS 运行时（Xposed 宿主）写了 hook：

```js
Java.hook(WebViewUI, "onCreate", {
  after(call) {
    const intent = call.thisObject.getIntent();     // ← 致命的两行
    const url = intent.getStringExtra("rawUrl");
  }
});
```

**结果：微信直接卡死，随后整个进程 abort。**

崩溃栈：

```
JNI<false>::GetObjectField  ← 对一个已失效的 jobject 读字段
libquickjs.so (Java_com_dokar_quickjs_QuickJs_invokeJsFunction)
art::JavaVMExt::JniAbort
```

教训：**在 hook 回调里不能再进 Java**。这个运行时的 bridge 不可重入，`call.args[0]` 这种参数访问本身也会过桥。

退一步只 hook `loadUrl`（只读参数、不调 Java），**依然卡死**。

结论：在这台设备 + 这个运行时上，**任何 hook 都不可靠**，放弃注入路线。

---

## 3. 转向：不注入，只观察

既然不能 hook，就改成"从外部观察"。三个候选：

| 通道 | 结论 |
|---|---|
| logcat | 微信只打 DNS 日志，不打 URL |
| XWeb 历史库 | 根本不存在 `History` 文件 |
| **XWeb Cookie 库** | ✅ 命中 |

`/data/data/com.tencent.mm/app_xweb_data/Profile 1/Cookies` 是一个 SQLite，里面存着：

```
session = base64({"openId":"<32位hex>"})
```

**openid 就在 cookie 里**。而且它只在页面加载后写入——不需要 hook，root 直接读文件即可。

> 注意：有 `Default/` 和 `Profile 1/` 两个 profile，实际生效的在 `Profile 1`。

## 4. 怎么让它"自己"重新走一次授权

关掉页面后重新 `am start` 微信的 `WebViewUI`，发现**不会重新授权**——微信只是把已有页面拉到前台。

必须加 flag 强制新实例：

```bash
am start -f 0x18000000 \           # NEW_TASK | MULTIPLE_TASK
  -n com.tencent.mm/.plugin.webview.ui.tools.WebViewUI \
  --es rawUrl "$OAUTH_URL"
```

再加上 root 身份（uid 0 可绕过 `exported=false` 的检查），就能把任意 URL 塞进微信的 WebView。

授权地址来自公众号菜单，内存里能扫到：

```
open.weixin.qq.com/connect/oauth2/authorize?appid=…&redirect_uri=…&scope=snsapi_base…
```

关键点：`scope` 必须是 **`snsapi_base`**（静默）。用 `snsapi_userinfo` 会多一次授权确认，锁屏下几乎必失败。

## 5. Cookie 什么时候落盘（踩坑）

一开始"打开页面 → 等 30 秒 → 读 cookie"，一轮要 33 秒，盲区太大。

实测发现：**关闭页面的动作会立即触发 Cookie 刷盘**。

```
打开授权页 → 等 8 秒 → 关闭页面 → 2 秒内 cookie 就有了
```

一轮从 33 秒降到 **12 秒**。

另一个坑：Cookie 落盘有微小延迟，如果读得太早会读到**上一轮**的值（刚被顶掉、必然 401）。所以必须"先记录旧集合，只认新增的值"。

## 6. 锁屏为什么不能用

三个独立原因，逐个踩出来的：

**① 状态判断漏了 `Dozing`**

```bash
dumpsys power | grep mWakefulness
# Awake / Dozing / Asleep
```

熄屏不是直接进 `Asleep`，而是先 `Dozing`。只判断 `Asleep` 的话，唤醒逻辑永远不触发。

**② 内核 suspend 会冻住 `sleep`**

熄屏后设备 suspend，进程的定时器全停。日志上看不出来，但轮询从 5 秒退化成 33~38 秒。

解法：写内核 wakelock

```bash
echo tm_sign > /sys/power/wake_lock      # 持有
echo tm_sign > /sys/power/wake_unlock    # 释放
```

按时段持有（默认 07:00–23:00），夜间释放省电。

**③ WebView 在锁屏下不加载**

所以续号前要先唤醒：

```bash
input keyevent 224        # WAKEUP
wm dismiss-keyguard       # 无安全锁时有效
… 续号 …
input keyevent 223        # SLEEP
```

## 7. 通知为什么从来没出现过

`cmd notification post` 执行成功、无报错，但通知栏什么都没有。

原因：**uid 0 发的通知会被系统静默丢弃**。

```bash
su -c "cmd notification post …"        # 消失
adb shell "cmd notification post …"    # 正常
su 2000 -c "cmd notification post …"   # 正常
```

解法：root 进程里降权发送

```sh
su 2000 -c "sh /data/local/tmp/tm_notify.sh"
```

（消息先写文件再由降权脚本读取，避免 JSON 里的双引号破坏命令行。）

同一个坑还有一个变体：`tinyplay` 直接播 WAV 也失败——能打开 `/dev/snd/pcmC0D0p` 但写入报错，SELinux 域 `u:r:ksu:s0` 不放行，`runcon` 换域也被拒。最后放弃自播音频，改用通知通道自带的提示音。

## 8. 接口是怎么挖出来的

没有抓包工具（PC 出不了网），直接读前端 bundle：

```bash
# 页面里 SSR 注入了完整的环境变量
window.process.env = { API_BASE_URL: "https://www.teachermate.com.cn", … }
window.__ASSET_MANIFEST__ = { … }   # 所有 chunk 的地址

# 拉下所有 chunk，grep 出接口路径
grep -o '"/v1/[a-z/-]*"' *.chunk.js
```

拿到：

```
/v1/class-attendance/student/active_signs
/v1/class-attendance/student/courses
/v1/class-attendance/student-sign-in
/v1/class-attendance/student/history?courseId=
```

提交报文格式从压缩后的组件代码里读出来：

```js
d = { courseId: u, signId: p };
if (isGPS > 0) { d.lat = …; d.lon = …; }
```

## 9. 幂等：`errorCode 305`

已经签过时，接口返回：

```json
{"errorCode":305,"msg":"repeat sign in","msgClient":"你已经签到成功"}
```

这不是失败，是**幂等成功**。如果当成失败处理，脚本会每 5 秒重发一次，把日志和服务器都刷爆。

必须显式识别：

```sh
*"repeat sign in"*|*"已经签到"*)  signed="$signId" ;;
```

---

## 10. 总结

| 原以为 | 实际 |
|---|---|
| hook 微信抄 URL | 这个运行时下 hook 必崩 |
| 抓一次 openid 长期用 | 15 分钟就废 |
| 熄屏时续号最"安静" | 熄屏时根本加载不了 |
| `cmd notification post` 能用 | uid 0 发的会被丢弃 |
| 通知里能自带自定义音效 | 只能用它自己的提示音 |

最终的架构是一条很窄的路：**root 拉起官方授权页 → 读官方 Cookie → 用官方接口**。不注入、不伪造、不改微信，稳定性全靠"不做多余的事"。
